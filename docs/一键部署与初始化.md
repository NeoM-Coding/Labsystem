# 一键部署与初始化

## 功能范围

[`scripts/deploy.sh`](../scripts/deploy.sh) 负责启动 `compose.yml` 中的基础设施和 Java 微服务，并执行以下初始化：

1. 等待 MySQL 和 Permify 就绪。
2. 幂等执行 `sql/schema.sql`。
3. 向 MySQL 创建或更新默认超级管理员。
4. 根据 checksum 按需上传 `auth/schema/lab-system-v2.perm`。
5. 写入 `app:global#super_admin@user:{userId}` Permify relation。
6. 构建并启动 `base`、`mqtt`、`rule-engine`、`web` 四个微服务。

`edu` 当前没有 RPC 契约或常驻任务，启动后会直接退出，因此暂不作为微服务容器运行。

## 使用方法

完整部署需要 Docker Compose 和 Java 17。Java 仅用于在宿主机通过 Maven Wrapper
构建 JAR，应用进程运行在 Compose 的 Java 容器中。

首次运行会自动从 `.env.example` 创建 `.env`：

```bash
./scripts/deploy.sh
```

建议先手动创建并修改配置：

```bash
cp .env.example .env
./scripts/deploy.sh deploy
```

其他命令：

```bash
./scripts/deploy.sh infra
./scripts/deploy.sh apps
./scripts/deploy.sh build
./scripts/deploy.sh hot-reload
./scripts/deploy.sh bootstrap
./scripts/deploy.sh status
./scripts/deploy.sh logs
./scripts/deploy.sh down
```

- `infra` 只启动基础设施并完成 MySQL/Permify 初始化。
- `apps` 要求基础设施已经运行，随后构建 JAR 并使用 `--no-deps` 启动应用容器，不会重建基础设施。
- `build` 只重新打包四个微服务。若应用容器正在运行，JAR watcher 会自动重启对应 JVM。
- `deploy` 依次执行基础设施启动、初始化、JAR 构建和应用启动。

所有启动操作都基于固定 Compose project `lab-system-cloud`，重复执行 `up -d` 会复用已有容器。应用阶段显式使用 `--no-deps`，不会间接操作 MySQL、Redis、Nacos 等基础设施容器。

## JAR 热更新

四个应用容器挂载对应模块的整个 `target/` 目录，而不是挂载单个 JAR：

```text
base/target        -> base-service:/app/artifacts
mqtt/target        -> mqtt-service:/app/artifacts
rule-engine/target -> rule-engine-service:/app/artifacts
web/target         -> web-service:/app/artifacts
```

挂载目录可以正确观察 Maven 以新文件替换旧 JAR 的行为。容器内的
`infra/java/hot-reload.sh` 会等待 JAR 写入稳定，然后向旧 JVM 发送 `SIGTERM`，并在同一个容器内启动新 JAR。容器 ID、网络地址和基础设施容器均保持不变。

开发时执行 `./scripts/deploy.sh hot-reload`，脚本会监听各模块的 `pom.xml` 和
`src/main`。源码变化后自动重新打包，容器内的热更新脚本会继续完成 JVM 重启；
按 `Ctrl+C` 只停止源码监听，不会停止已经运行的容器。

修改代码后可以直接执行：

```bash
./scripts/deploy.sh build
```

也可以只构建一个模块及其依赖：

```bash
./mvnw -pl web -am package -DskipTests
```

对应容器通常会在 `HOT_RELOAD_INTERVAL_SECONDS + HOT_RELOAD_SETTLE_SECONDS` 后加载新 JAR。

脚本不会在 `down` 时删除 volume。需要清空数据时应明确执行 Docker Compose 的 volume 删除操作。

## 默认管理员密码

部署脚本不会现场计算 BCrypt，也不会把明文密码直接写入 MySQL。`.env` 中同时保存登录说明和由 Java Test 预编译的 BCrypt 摘要：

```dotenv
SUPER_ADMIN_PASSWORD='Admin@123456'
SUPER_ADMIN_PASSWORD_BCRYPT='$2a$...'
```

修改密码时，先运行测试生成摘要：

```bash
source ~/.zshrc
./mvnw -pl base -am \
  -Dtest=SuperAdminFixtureTests \
  -Dsuper.admin.password='新的密码' \
  -Dsurefire.failIfNoSpecifiedTests=false test
```

将测试输出的 `SUPER_ADMIN_PASSWORD_BCRYPT` 写入 `.env`，并同步修改 `SUPER_ADMIN_PASSWORD`。正常测试会验证 `.env.example` 中两者一致。

## 幂等边界

- MySQL schema 使用 `CREATE TABLE IF NOT EXISTS`。
- 超级管理员按 username 查找；重复部署会刷新密码摘要、邮箱、备注和软删除状态。
- 若配置的用户 ID 或显示名称已被其他用户占用，脚本会失败而不是覆盖该用户。
- Permify 使用独立 PostgreSQL volume 持久化 schema、relation 等授权数据。
- DSL checksum 未变化且已记录的 version 仍存在时，bootstrap 会复用原 version。
- DSL 变化或 Permify PostgreSQL 被清空时，bootstrap 会上传新 version。
- Super Admin relation 写入前会先读取，已存在时跳过。

Permify 官方持久化数据库使用 PostgreSQL，不支持直接复用本项目 MySQL。Compose 中的 `permify-postgres` 只归 Permify 使用；业务数据、默认管理员和 bootstrap checksum 仍保存在 MySQL。执行普通 `down` 不会删除两类数据库 volume。
